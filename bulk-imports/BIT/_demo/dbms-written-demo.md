Q: Define a database management system (DBMS) and explain any four advantages of using a DBMS over traditional file-based systems.
TYPE: written
MODEL_ANSWER: A Database Management System (DBMS) is software that creates, organizes, stores, retrieves, and manages data in a structured way, sitting between the physical data and the applications/users that need it, and enforcing rules that keep that data consistent, secure, and accessible through a query language such as SQL. Four key advantages over traditional file-based systems: (1) Reduced data redundancy and inconsistency — a DBMS centralizes data so the same fact isn't duplicated across many files, which also prevents the update anomalies that occur when only some copies get changed. (2) Data integrity and enforced constraints — primary keys, foreign keys, and check constraints stop invalid or contradictory data from ever being stored, something file systems cannot enforce automatically. (3) Concurrent access control — a DBMS uses locking and transaction protocols so multiple users can safely read and write data at the same time without corrupting it, whereas flat files have no built-in mechanism for this. (4) Better security and backup/recovery — a DBMS provides authentication, user-level access privileges, and structured backup/recovery (e.g. via transaction logs), giving far stronger protection than access control on raw files in an operating system.

Q: What is an Entity-Relationship (ER) diagram? Differentiate between an entity, an attribute, and a relationship, and illustrate with an example from a university database.
TYPE: written
MODEL_ANSWER: An Entity-Relationship (ER) diagram is a conceptual modeling tool used to visually represent the data requirements of a system before it is translated into a relational schema. An entity is a real-world object or concept that can be distinctly identified and about which data is stored — for example, STUDENT or COURSE in a university database; entities are drawn as rectangles. An attribute is a property or characteristic that describes an entity — for example, student_id, name, and date_of_birth describe the STUDENT entity; attributes are drawn as ovals connected to their entity, with the key attribute underlined. A relationship describes an association between two or more entities — for example, ENROLLS_IN connects STUDENT and COURSE, capturing the fact that a student registers for a course; relationships are drawn as diamonds and carry their own cardinality (e.g. one student can enroll in many courses, and one course can have many students — a many-to-many relationship). Together, entities, attributes, and relationships let a designer capture the full structure of the data before worrying about tables, keys, or normalization.

Q: Explain the concept of normalization. Describe the First, Second, and Third Normal Forms (1NF, 2NF, 3NF) with a short example of a table that violates each and how it is corrected.
TYPE: written
MODEL_ANSWER: Normalization is the systematic process of organizing the columns and tables of a relational database to reduce data redundancy and eliminate undesirable insertion, update, and deletion anomalies, by progressively decomposing tables according to a series of normal forms. First Normal Form (1NF) requires that every column hold only atomic (indivisible) values and that there be no repeating groups — a table storing "Phone: 9841111111, 9847777777" in a single cell violates 1NF; it is corrected by splitting the phone numbers into separate rows or a separate related table. Second Normal Form (2NF) requires the table to already be in 1NF and that every non-key attribute be fully functionally dependent on the whole primary key, not just part of it — this only matters for composite keys; e.g. a table keyed on (student_id, course_id) that also stores student_name (which depends only on student_id, not on course_id) violates 2NF, and is corrected by moving student_name into a separate STUDENT table. Third Normal Form (3NF) requires the table to already be in 2NF and that there be no transitive dependency of non-key attributes on the primary key through another non-key attribute — e.g. a table with (student_id, department_id, department_head) where department_head depends on department_id rather than directly on student_id violates 3NF, and is corrected by moving department_id and department_head into a separate DEPARTMENT table referenced by a foreign key.
EXPLAIN: Marking scheme (10 marks total): 2 marks for defining normalization and its purpose (reducing redundancy/anomalies); for each normal form (1NF, 2NF, 3NF) — 1 mark for a correct rule statement and 1.66 marks for a correct violating example plus its correction (approx. 2-3 marks per NF). Award full marks only if the example genuinely violates that specific normal form and the correction actually resolves it.

Q: What are the ACID properties of a database transaction? Explain each property with a brief real-world example.
TYPE: written
MODEL_ANSWER: ACID is an acronym describing four properties that guarantee reliable processing of database transactions. Atomicity means a transaction is treated as a single indivisible unit — either all of its operations succeed and are committed, or none of them are, so a bank transfer that debits one account but crashes before crediting the other is fully rolled back rather than left half-done. Consistency means a transaction takes the database from one valid state to another valid state, preserving all defined rules and constraints — e.g. a transaction cannot leave an account with a negative balance if that violates a check constraint. Isolation means concurrently executing transactions do not interfere with each other's intermediate (uncommitted) state, as if each transaction ran alone — e.g. two customers booking the last airline seat simultaneously must not both succeed; isolation ensures one transaction's partial changes are invisible to the other until commit. Durability means once a transaction is committed, its changes survive permanently even in the event of a system crash or power failure, typically guaranteed via write-ahead logging — e.g. a confirmed money transfer remains recorded even if the server crashes one second later.

Q: Differentiate between INNER JOIN, LEFT OUTER JOIN, and RIGHT OUTER JOIN in SQL, and write a short SQL example using two tables, STUDENT(student_id, name) and ENROLLMENT(student_id, course_id), to demonstrate a LEFT OUTER JOIN.
TYPE: written
MODEL_ANSWER: An INNER JOIN returns only the rows where there is a matching value in both joined tables — students with no enrollment record, or enrollments referencing a non-existent student, are excluded entirely. A LEFT OUTER JOIN returns all rows from the left table plus the matching rows from the right table; where there is no match, the right table's columns appear as NULL — so every student appears at least once, even one who has not enrolled in any course. A RIGHT OUTER JOIN is the mirror image: it returns all rows from the right table plus matching rows from the left table, filling unmatched left-side columns with NULL. Example LEFT OUTER JOIN: SELECT STUDENT.student_id, STUDENT.name, ENROLLMENT.course_id FROM STUDENT LEFT OUTER JOIN ENROLLMENT ON STUDENT.student_id = ENROLLMENT.student_id; — this returns every student, with course_id shown as NULL for any student who is not currently enrolled in a course.

Q: What is an index in a database? Explain how a B+ tree index improves query performance, and mention one drawback of having too many indexes on a table.
TYPE: written
MODEL_ANSWER: An index is an auxiliary data structure built on one or more columns of a table that allows the database engine to locate rows matching a search condition without scanning every row in the table, much like an index at the back of a book lets you jump directly to a topic instead of reading every page. A B+ tree index organizes keys in a balanced, sorted tree where all actual data pointers are stored in the leaf nodes, which are also linked together in sorted order; internal nodes hold only routing keys used to navigate down to the correct leaf. This structure improves query performance because it guarantees logarithmic-time lookup (O(log n)) for equality and range queries, regardless of table size, and because the linked leaf nodes make range scans (e.g. WHERE age BETWEEN 20 AND 30) very efficient, unlike a full table scan which is O(n). The main drawback of having too many indexes on a table is write overhead: every INSERT, UPDATE, or DELETE must also update every index defined on the affected columns, which slows down write-heavy workloads and increases storage space, so indexes should be created selectively on columns that are actually queried or joined on frequently.

Q: Explain the concept of deadlock in a database system. Describe any two techniques used to prevent or resolve deadlocks.
TYPE: written
MODEL_ANSWER: A deadlock occurs in a database when two or more transactions are each waiting for a lock held by the other, so that none of them can ever proceed — for example, Transaction A holds a lock on row 1 and waits for a lock on row 2, while Transaction B holds a lock on row 2 and waits for a lock on row 1; both transactions are stuck forever unless the system intervenes. Two common techniques to prevent or resolve deadlocks: (1) Deadlock prevention via lock ordering — the system requires all transactions to acquire locks on resources in a globally agreed, consistent order (e.g. always lock lower row-ids before higher ones); since no transaction can then hold a "later" lock while waiting for an "earlier" one, a circular wait can never form, which prevents deadlock before it happens. (2) Deadlock detection and recovery via a wait-for graph — the database periodically builds a graph where each node is a transaction and each edge represents "transaction X is waiting for a lock held by transaction Y"; if this graph contains a cycle, a deadlock exists, and the system resolves it by choosing a "victim" transaction (typically the one that has done the least work or holds the fewest locks) and rolling it back, releasing its locks so the remaining transactions can proceed.

Q: What is database normalization trying to avoid? Using a single unnormalized table ORDER(order_id, customer_name, customer_address, product_id, product_name, quantity, price), identify two specific anomalies (insertion, update, or deletion) that this table structure would suffer from, and explain each.
TYPE: written
MODEL_ANSWER: Normalization is trying to avoid data redundancy and the three anomalies that redundancy causes: insertion anomalies, update anomalies, and deletion anomalies. In the given ORDER(order_id, customer_name, customer_address, product_id, product_name, quantity, price) table: (1) Update anomaly — because customer_name and customer_address are repeated on every order row for that customer, if a customer changes their address, every single order row for that customer must be updated; if even one row is missed, the table now holds two different addresses for the same customer, an inconsistent state. (2) Deletion anomaly — if a customer has placed only one order and that order row is deleted (e.g. the order is cancelled and removed), the customer's name and address are lost from the database entirely, even though the customer as a person still exists; deleting order information should not accidentally delete customer information. (A third valid answer: an insertion anomaly — a new product cannot be added to the catalog with its product_name and price until at least one customer places an order for it, since product details only exist attached to an order row.)

Q: Explain the difference between a primary key, a candidate key, and a foreign key with an example.
TYPE: written
MODEL_ANSWER: A candidate key is any minimal set of one or more attributes that can uniquely identify each row in a table — a table can have multiple candidate keys; for example, in a STUDENT table, both student_id and email could each independently and uniquely identify a student, making both candidate keys. A primary key is the one candidate key that the database designer selects as the main, official identifier for the table; once chosen, it cannot contain NULL values and is used by default for indexing and as the target of foreign key references — e.g. student_id is chosen as the primary key of STUDENT, while email remains an unused (alternate) candidate key. A foreign key is an attribute (or set of attributes) in one table that references the primary key of another table, establishing and enforcing a link between the two tables — e.g. in an ENROLLMENT(student_id, course_id) table, student_id is a foreign key referencing STUDENT.student_id, ensuring that no enrollment can reference a student who does not actually exist.

Q: What is a distributed database? Explain data fragmentation and data replication as two strategies for distributing data across sites, including one advantage and one disadvantage of each.
TYPE: written
MODEL_ANSWER: A distributed database is a single logical database whose data is physically stored across multiple, possibly geographically separate, computer sites connected by a network, while still being managed and queried as if it were one unified database. Data fragmentation splits a table into smaller pieces (fragments) — horizontally (by rows, e.g. customers from Asia stored at the Asia site and customers from Europe at the Europe site) or vertically (by columns) — and stores different fragments at different sites. Advantage: fragmentation improves performance and locality, since a site mostly queries the data relevant to its own region, reducing network traffic; disadvantage: queries that need data spanning multiple fragments (e.g. a global report across all regions) require expensive cross-site joins and coordination. Data replication instead stores full or partial copies of the same data at multiple sites. Advantage: replication improves availability and read performance, since a query can be served by the nearest or least-loaded copy, and the system tolerates a site failure because other replicas still hold the data; disadvantage: replication introduces the overhead and complexity of keeping all copies consistent whenever the data is updated, which can cause temporary inconsistency or added write latency depending on the consistency model chosen.
